# PRODUCT.md

## 1. Product summary

**QuizParty** is a Greek-first party trivia game for Windows and Android. It can be played on one device or across multiple devices on the same local network. A PC connected to a monitor/TV can act as the shared presentation screen while phones act as private controllers.

Brand name: **QuizParty** (one word, capital Q and P). Greek-first describes the
initial language/content focus and is not part of the game name.

The game differentiates itself through **strategy and social chaos**, not only factual recall. Players choose how strongly to bet on their knowledge, build streaks, earn limited power cards, complete secret missions and can recover from a weak start without pure random rubber-banding.

## 2. Target audience

Primary:

- Greek-speaking friends and families.
- House parties and gatherings.
- Couples or small groups wanting a fast casual game.
- Players who enjoy trivia but want more interaction than a basic Q&A app.

Secondary:

- Schools and informal education settings.
- Greek diaspora households.
- Streamers or community events using a PC/TV as host screen.

## 3. User value proposition

### Player value

- Start quickly without account creation.
- Works even without Internet.
- Everyone can use a phone instead of passing one device around.
- Questions are Greek-first and culturally relevant.
- Strategic decisions create memorable moments and comebacks.

### Host value

- Simple Create Game flow.
- Automatic discovery on the same Wi-Fi/LAN.
- Room PIN and clear lobby control.
- Host can choose categories, game length, teams and enabled mechanics.

## 4. Product principles

### 4.1 Offline-first

All normal local/LAN gameplay must work without Internet access.

### 4.2 No account required

A player enters a display name and chooses one of eight characters. Characters are unique within a lobby, including host and local players. No mandatory registration.

### 4.3 Fast lobby

From app launch to playable lobby should normally require less than one minute.

### 4.4 Fair but dramatic

Power-ups may create tactical swings, but they must not invalidate knowledge. Correct answers remain the main path to winning.

### 4.5 Host authority

The host is the source of truth for timing, question selection, answer correctness, scoring, power-ups and game-state transitions.

### 4.6 Data-driven content

Questions, categories, difficulty labels and explanations must be content files, not hardcoded in scenes.

### 4.7 Accessible UX

Do not rely only on color to convey correctness. Buttons must be large enough for touch. Timers must have clear visual and textual states. Support reduced motion as a setting.

## 5. Core use cases

### UC-01: Single-device party

2–8 players share one Windows or Android device. The game rotates or presents inputs appropriate to the selected local mode.

### UC-02: Windows host + phone controllers

The host creates a room on Windows. Phones discover the host, join the lobby, choose names and answer on their own screens.

### UC-03: Mixed local and remote players

Two people can play locally on the host PC while three others join from phones. `PlayerId`, `ConnectionId` and `LocalSlot` are distinct concepts.

### UC-04: Team game

Players are assigned to teams. Scoring aggregates to team score, while individual stats may still be tracked.

### UC-05: Quick Game

A short 10-question experience with minimal setup.

### UC-06: Full Game

Multiple rounds, category variation, confidence choices, streaks, Chaos Cards, secret missions and a final scoreboard.

## 6. Functional requirements

### 6.1 Main menu

- Play
- Host Game
- Join Game
- Solo
- Settings
- Question Packs / Content information
- Credits
- Exit (Windows)

### 6.2 Lobby

- Room name.
- Room PIN optional.
- Player list.
- Ready state.
- Host indicator.
- Team assignment when Team Mode is enabled.
- Game rules summary.
- Kick player (host only).
- Start game (host only, based on configured minimum players).

### 6.3 Discovery

- UDP broadcast/multicast-style LAN discovery.
- Discovery-first participation screen. Manual-IP implementation is retained internally and hidden from the normal UI by user decision (2026-10-25).
- Display room name, player count, compatibility/protocol status and ping if practical.
- Ignore incompatible protocol versions.

### 6.4 Match

- Round intro.
- Question presentation.
- Confidence selection when enabled.
- Answer input.
- Lock state after submit.
- Server-side deadline validation.
- Reveal.
- Explanation/fact.
- Score update.
- Streak update.
- Optional Chaos Card usage.
- Secret Mission progress.
- Round summary.
- Final results.

### 6.5 Reconnection

V1 should support short LAN reconnects where reasonably safe:

- Player identity uses a session token generated by host.
- A reconnecting client may reclaim a disconnected player slot before timeout.
- Host decides whether reconnect is accepted.
- Never allow a reconnect to submit twice for the same question.

If reconnect proves unstable, shipping v1 with a clear “player disconnected” flow is preferable to unsafe state recovery.

## 7. Non-functional requirements

### Performance

- 60 FPS target on ordinary desktop hardware.
- Stable UI on mid-range Android devices.
- No frame-dependent game rules.
- Avoid per-frame allocations in hot paths.

### Reliability

- Network disconnects must not crash host.
- Invalid network messages are rejected safely.
- Missing/corrupt question packs produce actionable errors.
- Save/settings corruption falls back to defaults.

### Security/trust boundary

- LAN clients are untrusted.
- Client cannot set score.
- Client cannot reveal correct answer before host reveal.
- Client cannot choose authoritative random results.
- Validate IDs, state, timing and one-answer-per-question constraints.

### Privacy

- No account required.
- No telemetry in MVP unless explicitly added later.
- Do not collect device identifiers unnecessarily.

## 8. Success metrics for internal beta

- Host + 4 clients can complete 30 questions without desync.
- 10 consecutive full matches without crash on test devices.
- Join success on typical home router/Wi-Fi setups.
- Median “create room to first question” under 90 seconds for new testers.
- At least 90% of content validator checks pass before manual editorial review; public release requires 100% automated validation.

## Approved participation flow — 2026-10-25

Home uses «Δημιουργία» and «Συμμετοχή». Participation opens «Διαθέσιμες Αίθουσες»
with icon-only corner Back and refresh beside the heading. Room rows show name
and joined/max count. PIN remains optional: protected rooms ask in a popup;
unprotected rooms go directly through host preflight to identity selection.
Wrong PIN closes the popup and shows an error in the rooms list.

Successful preflight does not create a player, count a joined seat, or reserve a
character. Identity screen collects name and character. Taken characters are
visibly greyed and disabled. The host atomically validates the final join; a
simultaneous loser keeps their name, sees a character-conflict message and chooses
from refreshed availability. The join action uses an icon and accessible name.
All eight slots, including host and shared-device players, obey uniqueness.

Portrait/landscape Android inputs must remain visible above the virtual keyboard.
These decisions explicitly authorize the necessary lobby/protocol changes within
the current phase; manual-IP transport remains available for possible future UI.

## Optional host player and room capacity — 2026-10-25

User approved a rendered host with no player seat ("headless" in this UI's terms).
Host authority remains transport connection 1; its roster player is optional.
A non-playing host owns no character, readiness, team membership, score, answers,
hand or mission. It controls setup and progression and renders a public match
projection only. It does not occupy one of the 2–8 configured actual-player slots.
A match still requires at least two actual players, all ready.

Creation now has room name, always-visible optional PIN, maximum players (2–8),
and whether the host participates. Participating hosts continue to the same
name/character form used by joining clients, then create the room. Non-playing
hosts create immediately. Character-list overflow scrolls independently, while
name and submit remain outside it. Scrollbars are hidden; scrolling remains usable.
